# deepseek-memory

[English](README.md) | 中文

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的**长期记忆**
插件，以可安装的社区 bundle 形式交付。

这里的"记忆"是**少而精的沉淀**，不是对话记录索引：库里只存有限条关于用户和项目的
短事实，并且**整库注入每一次请求**。正是这个"有界"消掉了检索问题——不需要 embedding
服务、不需要排序、也不会在会话历史里留下陈旧快照。

记忆库同时也是一个**信任边界**：库里的文本是模型写入的，之后又会读回提示词。
本插件对此是认真的——写入原子化且加锁，记忆文本以"数据"而非"指令"的身份注入，
越界或伪造的内容被拒绝而不是悄悄截断。详见下文[安全模型](#安全模型)。

## 为什么需要记忆

没有记忆层，每个新会话都从零开始：

| 第几天 | 你说 | AI 的做法 |
| --- | --- | --- |
| 1 | "我用 pnpm，不用 npm。" | 用了 pnpm ✅ |
| 5 | *（什么也没说）* | 又用回 npm ❌ |

有了 deepseek-memory，第 5 天不一样：

| 第几天 | 你说 | AI 的做法 |
| --- | --- | --- |
| 1 | "我用 pnpm，不用 npm。" | `memory_add`："用户用 pnpm。" |
| 5 | *（什么也没说）* | 仍然用 pnpm ✅——记忆库注入了每一次请求 |

一个事实只说一次，之后的每个会话都会带着它。不用反复交代，不用"我之前说过"。

## 功能

| 部件 | 行为 |
| --- | --- |
| **两层记忆** | `user`（`$DSH_HOME/memory/`）记"这个人是谁"；`project`（`<cwd>/.dsh-memory/`）记这个仓库的约定与决策。 |
| **工具** | `memory_add`、`memory_update`、`memory_delete`、`memory_list`、`memory_search`、`memory_status`。 |
| **注入** | 一个 `systemPrompt` 区段，其 `text` 是**每次装配时求值的 provider**。不往会话历史里写任何东西。 |
| **轮末整理** | 由一个**受限 child agent** 只通过记忆工具审阅刚结束的那一轮。 |
| **明文存储** | 库是可读 JSON，可手改、可 git diff；每次改动保留上一版。 |

## 安装

```sh
dsh plugin --profile web add github:RocoFish/deepseek-memory
```

**没有构建步骤，也不需要你放行任何脚本**——因为本仓库**把编译产物 `lib/` 提交进了
版本控制**，从 git 源安装直接拿到编译好的插件。这是一个有意的取舍：把构建产物
放进版本控制并不常见，代价是维护者每次推送前要重新构建一次；换来的是每个使用者都不必先读
一遍 pnpm 的构建脚本报错、再手工编辑 `pnpm-workspace.yaml`。一个要给别人装的插件，安装
就得是一条命令。

也就是说，**本包刻意不声明 `prepare` 脚本。** pnpm 判断一个 git 依赖的构建脚本是否需要
放行，靠的是 `package.json` 里**有没有这个条目**——在执行之前判断，且与里面写了什么无关。
所以一个"`lib/` 已存在就直接退出"的条件式 `prepare` 照样会要求放行，这一点是实测出来的，
不是推断。真正能去掉这一步的做法就是：提交 `lib/`，并删掉那个条目。`prepublishOnly` 仍然
会在发布 npm 包时构建，那条路径不影响任何使用者。

贡献者克隆仓库后没有 `lib/`（也可以自行删除），用 `npm install && npm run build` 构建即可。

装完重启该 profile。

## 3 步验证（约 5 分钟）

- [ ] **1. 安装并重启 profile**（命令见上）。
- [ ] **2. 检查两层状态**——让模型运行 `memory_status`。每一层都会报告自己的位置和
      条目数；定位失败的层会被**显式报告为已禁用**，而不是悄悄消失。
- [ ] **3. 写入，再开新会话召回**——说"用 `memory_add` 记住：我用 pnpm，不用 npm。"
      确认条目出现在 `memory_list` 里，然后**新开一个会话**直接问
      "我用哪个包管理器？"它应该不需要提醒就答得出来。

第 3 步答上来了，插件就是装好了。哪一步卡住，看[已知边界](#已知边界)。

## 配置

每个键都能在 profile 的 `cordis.patch.yml` 里针对 `memory` 这一行覆盖：

```yaml
- id: memory
  config:
    maxEntries: 80
    consolidation: always
```

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `user` | `true` | 启用用户级记忆层。 |
| `project` | `true` | 启用项目级记忆层。 |
| `maxEntries` | `50` | 每层最大条数。 |
| `maxEntryChars` | `500` | 每条最大字符数。 |
| `injectChars` | `4000` | 单次请求注入的最大字符数。 |
| `tools` | `true` | 注册记忆工具。 |
| `consolidation` | `gated` | `off`、`gated` 或 `always`。 |
| `minTurnsBetweenRuns` | `1` | 同一会话两次整理之间的最小已结束轮数。 |
| `keepHistory` | `true` | 在 `history/` 里保留上一版。 |
| `consolidationSubagentProvider` | `in-process` | 整理 **child** 运行的 subagent provider 名。注意这是 provider **名**，不是模型路由。 |
| `consolidationRouteProvider` | — | **退化路径**的 provider 路由，仅在没挂 subagent provider 时使用；省略则复用会话自己记录的路由。 |
| `consolidationRouteModel` | — | 与上面配对使用的模型 id。 |
| `consolidationTimeoutMs` | `120000` | 单次整理运行的墙钟上限。 |

## 整理是怎么工作的

每一轮都花一次模型调用太浪费——绝大多数轮次里没有任何值得长期保留的东西。闸门是一段
**本地、确定性**的扫描，只认真正会改变长期记忆的情形：明确要求记住、纠正、长期偏好、
决策、约束。它**故意偏向漏触发**：漏掉的一次整理会被之后相关的一轮补上；而一个过度
积极的整理器最终会开始**编造记忆**。想要"每轮必整理"的字面行为，设
`consolidation: always`。

闸门放行后，整理以一个**受限 child agent** 运行：

- `toolFilter: { allow: [memory_*] }` 把其余所有工具从 child 的提示里**移除**，并在
  执行层**拒绝**——所以无论对话内容怎么诱导，它都读不到也写不了你的仓库；
- `persona` 给它一份"只管整理记忆"的职责说明，仅对这个 child 遮蔽部署 persona；
- `outputSchema` 让它返回一份结构化回执；
- 它**不继承父会话历史**，所以整理永远不会撑大主对话的上下文。

child 通过**本插件自己的工具**写记忆，所以每一条上限和每一条纠错文案照旧生效。这也正是
插件**不相信 child 自我报告**的原因：它比对运行前后的**库 revision**，把"声称改了但库
没动"当作失败。

当部署没有挂载 subagent provider 时，插件退化为一次直连模型请求 + JSON 改动集，由插件
逐条校验、限制单次条数、按层原子应用。child 路径严格更好；退化路径的存在是为了让没有
subagent 的部署也能整理。

## 安全模型

长期记忆插件必须把"记忆本身成为攻击面或损坏源"的情况挡在外面。威胁模型明说：
任何能操纵一段对话的人——网页或文档里埋的提示词注入、被污染的依赖产生的输出、
纯粹的社工——都有一条通往记忆库的通道，因为整理器的职责就是记下对话确立了什么。
所以设计目标**不是**把敌意文本挡在库外——对一个职责就是记录对话内容的记忆系统来说
这做不到。目标更窄，但可实现：

1. 被记住的文本永远不能获得**权威**——它始终是数据，不是指令；
2. 被投毒、伪造或损坏的库必须**响亮的、安全的失败**，绝不静默；
3. 写入方（整理器）必须是系统里受限制最多的组件；
4. 插件消耗的每一种资源都有上限，滥用只会降级，不会级联。

`main` 上目前成立的保证：

- **抗注入包装**。每条记忆文本注入时都被包在显式的 `<untrusted-data>` 边界内，
  并带有"这是数据，不是指令"的头部。包装标签本身在写入时即从条目文本里剥除——
  `memory_add` 和 `memory_update` **都剥**——所以已存的条目无法伪造闭合标签、
  突破自身容器、自我升格为系统指令。被记住的内容永远不会被当作命令执行，
  记忆读取的工具结果也不会被塑造成指令的形状。
- **拒绝而非截断**。加载时的校验对越界存储（条目数量/大小、标签数量/长度）直接
  拒绝，而不是悄悄保留一个坏掉的前缀。失败模式是**fail-closed**：非法的库会让
  该层在本次会话中停用并由 `memory_status` 明说，而不是给模型提供一份被任意
  截断的"关于用户已知事实"的局部视图。
- **原子化、串行化的写入**。提交运行在 per-tier 锁文件之下（陈旧锁 30 秒回收），
  锁内复检磁盘 revision，写盘用唯一临时文件 + rename——一次被打断的写入绝不会
  留下半个文件，两个写入方是串行化而不是交错执行。
- **拒绝丢失更新**。如果本会话加载之后另一个进程提交过同一层，写入会以
  `MEMORY_STORE_CONFLICT` 被拒绝，而不是静默丢掉对方的条目。并发写入的处理是
  **拒绝、然后重读**——绝不合并，因为两个模型写出的库做合并，本身又是一个注入面。
- **整理器读到什么也无法据此行动**。child agent 仅有的工具是 `memory_*`，其余
  工具在提示层移除、在执行层拒绝。一轮对话如果试图论证"先读这个文件 / 跑这条
  命令，再决定记什么"，会发现 child 根本没有这个能力；而 child 返回的回执也要
  对照库的**实际 revision** 核验，不信自我报告。
- **记忆层位置绝不靠猜**。两层都不回退到工作目录：用户层解析 `DSH_HOME` 和一条
  固定的 well-known home 链，项目层用会话自己经过校验的 `cwd`；定位不成立的层保持
  **关闭并明说**。这不止是卫生问题，也是安全问题——一个把自己静默锚定在宿主启动
  目录的层，可能被提交进共享仓库，通过一次公开 push 把个人事实**外泄**出去。
- **一切有界**。条目数、条目大小、标签数、标签长度、单次请求注入字符数、单次
  整理改动数、history 备份（20 个 / 5 MiB）、整理墙钟上限，全部有硬顶；资源型
  配置项钳制到这些硬顶，而不是信任操作者的输入。库不能被养成注入侧的上下文
  灌爆攻击，history 也不能把磁盘写满。
- **永不静默降级**。打包规则（`lib/` 零裸导入）由测试强制而不是靠约定，因为一条
  在真实安装上永远不触发的"优雅降级"，正是功能在插件报告健康时悄悄消失的原因。
  插件做不了自己的职责时，应该明说或关闭，绝不带病运行。

**刻意没有的：**

- **内容启发式的注入过滤**。对条目文本做正则或分类器筛查，能被任何读得到源码
  的人绕过——本仓库是公开的，即人人可读——还会贩卖虚假安全感，同时偶尔误伤
  合法记忆。上面"包装 + 权威分离"的模型才是真正的防御。
- **用户确认步骤**。整理器本就设计为无头自动运行；每轮结束都 interrupt 用户来
  批准一条关于他自己的事实，是本插件要消灭的失败模式。
- **事实核验**。库存的是对话说了什么（带来源 `origin` 标注），不是什么是真的。
  一条被整理进去的错误事实，其爆炸半径有界（条目小、可 `memory_list` 看见、
  可手改、可 git diff），但不会自动纠正。**审计记忆是用户习惯，不是插件功能。**

## 存储格式


```json
{
  "format": 1,
  "tier": "project",
  "revision": 3,
  "updatedAt": 1790000000000,
  "entries": [
    {
      "id": "m1a2b3c4",
      "text": "构建用 tsc，不用打包器。",
      "tags": ["build"],
      "createdAt": 1789990000000,
      "updatedAt": 1790000000000,
      "origin": "consolidator"
    }
  ]
}
```

`id` 由文本派生，所以同一个事实重复添加是幂等的，改写也保留身份。`format` 比当前
构建新的文件会被**拒绝**而不是猜着读。

项目层是给**用户在自己的仓库里**提交用的；不想共享就往项目的 `.gitignore` 里加
`.dsh-memory/`。

## 设计说明

有四条约束塑造了这个实现，改动前值得先知道。记忆模型本身——存什么、为什么——的
推理见 [DESIGN.md](DESIGN.md)。

**1. 没有万能的 `plugin` 消息来源。** `MessageSourceMap` 是可合并扩展的联合类型，
每个生产者**在自己的模块里声明自己的 `kind`**。写 `{ kind: 'plugin', plugin: 'x' }`
——旧版本接受的形状，而且在 harness 自己的测试夹具里到处都是——在 0.2 下**通不过类型
检查**，且在执行运行时强制的版本上会在日志边界抛
`format v4 message requires a producer-owned source kind`。本插件在
[`src/source.ts`](src/source.ts) 里声明自己的 kind。而注入**刻意完全不用消息注入**：
`systemPrompt` 的 provider 不可能在历史里留下陈旧副本。

**2. 轮次边界是 `agent/status` → `idle`，不是 `agent/turn-stopping`。** 后者是
serial 且被 await 的监听器，在那里整理会给**每一轮**都加上模型延迟。`agent/status`
是 `emit`，所以记忆工作发生在轮次已经关闭之后，没有任何东西在等它。

### 两层记忆的位置从哪里来

**项目层**取自会话自己记录的目录：`session/event` 的载荷里带着 `header`，其中 `cwd` 是经过
校验的绝对路径，也是唯一永远正确的来源。它通过 getter 按需解析，所以宿主切换项目时不用重启
插件也会跟随，并丢弃过期缓存；`apply` 时不缓存任何东西。

两个实测事实让这是唯一站得住的选择。第一，`ctx.get('cwd')` 在任何试过的宿主上都不是服务
——即使服务已注入也返回 `undefined`，所以那行查找从一开始就是死代码。第二，`process.cwd()`
描述的是宿主**怎么被启动的**，不是**哪个项目打开着**：同一个打包应用，一次启动得到
`D:\WSL\DSH Workspace`，另一次得到它自己的 profile 目录。信任它会把项目记忆静默写进应用
自己的配置目录——在项目里看不见，在别处又具有误导性。

**用户层**按下面的顺序解析，实际用到的来源由 `memory_status` 报告：

| 顺序 | 来源 | 为什么 |
| --- | --- | --- |
| 1 | `DSH_HOME` | 直接命名 harness home |
| 2 | `DSH_PROFILE_DIR` 上溯两级 | 应用公布的是 `<home>/profiles/<name>`，home 在上两级 |
| 3 | `USERPROFILE` + `.dsh` | Windows 标准 home 加 harness 自己的目录名 |
| 4 | `HOMEDRIVE` + `HOMEPATH` + `.dsh` | 路径被拆开的 shell |
| 5 | `dshHome` 服务 | 以服务形式而不是环境变量公布的宿主 |
| — | 否则**禁用** | 绝不回退到工作目录 |

第 2–5 条存在的原因是桌面应用的宿主主进程不携带 `DSH_HOME`：从同一个应用里派生的沙箱
shell 有这个变量，而宿主自己的启动环境没有，于是工具在 GUI 里报告该层缺失。回退到工作目录
依然被拒绝——那会把长期个人事实散落到宿主恰好启动的目录里，包括插件自己的检出，从而可能
被提交进仓库。

两层遵循同一条原则：**定位不成立的层保持关闭，并明说**。`memory_status` 会显式报告被关闭
的层，而不是省略它——否则"这一层缺失"和"这一层是空的"在输出里完全一样。

**3. 插件在运行时是自包含的，所以 SDK 只是类型依赖。**
`defineTool`、参数 schema 编译、参数校验、`createUserMessage`、输出 schema 检查，全部在本包
内实现，而不是 import 进来。SDK 包仍然声明着——作为 `peerDependencies` 表达版本一致性、作为
devDependencies 供类型检查和等价比对测试使用——但 `lib/` 里没有任何一处 import 它们，这正是
profile 安装能工作的前提。详见下文"产物自包含"。

**4. `ctx.get` 只在 `apply` 时读一次。** 与其说是要绕开的约束，不如说是要记住的事实：解析器
只读一次服务，所以插件需要的每个服务都必须列进 `inject`，不可能之后再发现。

### 结构接口 + 编译期一致性校验

插件对自己通过 `ctx` 触及的服务（`SubagentConsolidator`、工具注册表形状）声明的是**窄结构
接口**，而不是 import SDK 的服务类。运行时依赖面因此是零：产物 `lib/*.js` 不含任何裸说明符，
由 `tests/packaging.test.ts` 静态与动态双重把关。

结构接口有可能和真实接口悄悄漂移，所以
[`src/typecheck.ts`](src/typecheck.ts) 断言已发布的 `SubagentRuntime` 满足插件的接口。
**这个校验已经抓出两个真实错误**：一处 `readonly ContentBlock[]`（SDK 要求可变数组），
一处 `outputSchema` 类型过宽导致不可赋值。

### 产物自包含：零裸导入

这条打包规则决定 profile 安装到底能不能工作，而且在有人真的安装之前完全不可见。
它花了两轮调试才修好，所以完整链条记录在这里。

`dsh plugin add` 把本包放进 profile 的 `node_modules`，加载器从那里按名字 import 它。
裸 `@deepseek-ai/*` 说明符于是对着 **profile 自己的** `node_modules` 解析——那里只装
profile 声明的依赖，Harness SDK 住在安装目录里，不在那里。实测于 `desktop` profile：
`node_modules/@deepseek-ai` 不存在。所以顶层裸 import 不是降级，而是在任何一个钩子
注册之前就以 `failed to import` 让整个入口失败。

所以 SDK import 凡有可能**只留类型**，一切真实运行时需求都在本地实现：

| 需求 | 处理 |
| --- | --- |
| `createUserMessage` | 在 [`src/message.ts`](src/message.ts) 里复刻，契约在 `typecheck.ts` 里对着 SDK 自己的类型校验。 |
| `defineTool`（含参数编译、参数校验） | 在 [`src/define.ts`](src/define.ts) 里实现。 |
| `assertObjectJsonSchema` | 在 [`src/define.ts`](src/define.ts) 里实现为结构自洽性检查。 |

**带兜底的动态 `import()` 不是解法，本仓库已不再使用它。** 它看起来像优雅降级，但在
目标安装上这个 import 永远失败，于是"兜底"成了永久路径——功能静默缺失，插件却报告
健康。记忆工具从所有工具面上消失，正是这么发生的。

动态 import 还栽在第二个更隐蔽的原因上，值得知道：pnpm 用 **junction** 链接包，所以
`dsh-tools` 是从 `node_modules\@deepseek-ai\dsh-tools\lib\index.js` 进入的，而不是它的
真实 store 路径，于是它自己的 `import '@deepseek-ai/schemastery'` 从那里解析不出来——
尽管 schemastery *确实*作为同级链接装在 pnpm store 里：

```
ERR_MODULE_NOT_FOUND: Cannot find package '@deepseek-ai/schemastery'
  imported from ...\deepseek-memory\node_modules\@deepseek-ai\dsh-tools\lib\index.js
```

这是链接布局问题，**不是**已发布依赖闭包不完整。

这带来的唯一风险是和 harness 漂移，所以用两手压住：`tests/define.test.ts` 把同一份
选项过真 SDK 的 `defineTool` 编译一遍，并断言深度相等**包括键序**；`src/typecheck.ts`
断言本地定义始终可赋值给 SDK 自己的类型。`tests/packaging.test.ts` 强制 `lib/*.js`
里零裸说明符，静态**和**动态都算，所以这一点不会静默回归。

最后一个文件也是插件"验证过能工作"的原因：`defineTool` 是本地的，`createMemoryTools()`
在一个普通进程里、没有解析钩子、模块图上没有 SDK，也能返回全部六个工具。

## 常见问题

| 顾虑 | 回应 |
| --- | --- |
| **会不会污染我的项目？** | 不会。存储是你自己目录下的纯 JSON——可手改、可 `git diff`。项目层在 `<cwd>/.dsh-memory/`，不想共享就加进 `.gitignore`。 |
| **注入要花多少？** | 单次请求最多注入 `injectChars` 个字符（默认 **4000**），英文文本约合 ~1k token，路径上没有 embedding 或检索调用。 |
| **可逆吗？** | 可逆。`memory_delete` 可删任意条目；`keepHistory`（默认开）让每次改动在 `history/` 留上一版（上限 20 个文件 / 5 MiB）；卸载插件后剩下的只是普通文件。 |
| **库会无限增长吗？** | 不会。条目数、条目大小、标签数/长度、注入字符数、单次改动数、history 全部有硬顶——见[安全模型](#安全模型)。整理器过于积极时也被同一组上限压住。 |

## 已知边界

- **child 路径需要 subagent provider，退化路径需要模型路由。** 有 subagent provider 时
  child 继承会话模型，整理完全自动；没有的话退化路径需要 `consolidationRouteProvider` +
  `consolidationRouteModel`，或会话已记录的 `request/header` 路由；两者都没有时整理会
  **被跳过而不是猜一个模型**。
- **整理在进程内跑且不排队。** 一个会话同时只跑一次；运行中崩溃只丢那一次改动，
  不会丢已经提交的库。
- **并发写入是拒绝而不是合并。** 如果另一个进程在本进程加载之后提交了同一层（比如
  两个 harness 窗口开在同一个项目上），写入会被拒绝并返回 `MEMORY_STORE_CONFLICT`，
  同时丢弃过期的缓存，而不是悄悄覆盖另一方的条目。不 bump `revision` 的手改文件在
  `refresh()` 之前仍然不可见。
- **闸门是文本启发式。** 它只看用户与助手的文本，判断不了一轮是否**重要**，只能判断
  它是否**听起来**留下了可沉淀的东西。
- **不做近似去重。** 同一个事实的两种不同措辞算两条，靠整理器去合并。
- **`maxEntries` 是每层上限，不是全局上限**，所以两层都开时最多可存两倍的条目数。
- **child 只能写记忆，所以它得出的其他结论会被丢弃。** 这是有意为之，但也意味着"需要
  先读某个文件才能判断"的整理不在范围内。
